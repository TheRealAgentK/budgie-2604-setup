# gufw Wayland fix

## Symptom

Launching **Firewall Configuration** (gufw) does nothing: the polkit password
prompt appears, you authenticate, and no window opens. Nothing is logged to the
GUI.

Running it from a terminal shows:

```
Authorization required, but no authorization protocol specified
(gufw.py:NNNNN): Gdk-WARNING **: cannot open display:
```

## Root cause

gufw runs its **entire GTK GUI as root**:

```
gufw  ->  pkexec gufw-pkexec <user>  ->  (as root) python3 /usr/share/gufw/gufw/gufw.py <user>
```

It has to, because its backend also writes root-owned files under `/etc/gufw`
(rule store, app profiles, `/var/log/gufw.log`) in addition to shelling out to
`/usr/sbin/ufw`.

On a Wayland session the root process reaches the screen through Xwayland
(`DISPLAY=:1`). Xwayland here is started **without** an auth file and grants
access only to connections whose **UID matches the session user** — there is no
MIT-MAGIC-COOKIE anywhere to hand out. A process running as **root** is a
different UID, so Xwayland refuses it.

It used to work because the polkit policy
(`/usr/share/polkit-1/actions/com.ubuntu.pkexec.gufw.policy`) sets
`org.freedesktop.policykit.exec.allow_gui=true`, an Ubuntu downstream shim that
made `pkexec` forward `DISPLAY` / `XAUTHORITY` into the root environment. **That
shim was dropped in 26.04**, so the root process now starts with no path to the
display and exits silently.

## What the fix does

`bin/gufw` is a wrapper installed at `~/.local/bin/gufw` (ahead of
`/usr/bin/gufw` on `PATH`). It:

1. Adds `SI:localuser:root` to the running X server's access list
   (`xhost +SI:localuser:root`) — **only if it isn't already there**.
2. Runs `pkexec gufw-pkexec <user>` and waits.
3. On exit — normal close, crash, `SIGINT`/`SIGTERM`/`SIGHUP`, logout — revokes
   the grant (`xhost -SI:localuser:root`), but only if step 1 added it.

`applications/gufw.desktop` is installed at
`~/.local/share/applications/gufw.desktop`, overriding the system entry so the
menu item ("Firewall Configuration") and the `gufw` command both use the
wrapper. Being user-level, it survives `apt` upgrades of the `gufw` package.

Net effect: local-root X access exists **only while the firewall window is
open**, and nothing is left in autostart or in the X server between launches.

## Residual tradeoff

`xhost +SI:localuser:root` cannot be scoped to a single process. While the
firewall window is open, **any** process running as root can connect to the X
display (read keystrokes, capture the screen, inject input). That exposure is
inherent to gufw drawing its GUI as root; this wrapper only removes the
*permanent* version of the grant.

To avoid a root X client entirely:

- **Use the CLI:** `sudo ufw status verbose`, `sudo ufw enable`,
  `sudo ufw allow 22/tcp`, `sudo ufw status numbered` + `sudo ufw delete N`.
- **Switch to firewalld + firewall-config**, whose GUI runs as your user and
  escalates each privileged action over D-Bus/polkit. This replaces ufw (both
  drive nftables — run one).

## Install

```sh
./install.sh
```

Copies `bin/gufw` to `~/.local/bin/gufw`, then generates
`~/.local/share/applications/gufw.desktop` from the system entry with `Exec=`
pointed at the wrapper.

## Uninstall

```sh
./uninstall.sh
```

Removes both files. The menu item reverts to the system entry (which is still
broken on Wayland — that's expected).

## Verifying

```sh
# while the window is open:
DISPLAY=:1 xhost | grep root      # -> SI:localuser:root

# after closing it:
DISPLAY=:1 xhost | grep root      # -> (nothing)
```
